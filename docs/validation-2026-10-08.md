# 本地验证记录：2026-10-08

归档说明：以下记录是 0.9.0 发布准备之前的实验快照。清理工作目录后，原始实验目录已移至项目同级的 `py-roller-local-archive-20261008/py-roller-artifacts/`；下文实验路径均相对于归档前的项目目录，历史测试数量不代表最终发行检查结果。

本报告针对当前工作目录中的 0.8.3 + Unreleased 代码，不表示这些改动已发布。验证环境为 Apple M2、8 GB 内存、macOS arm64、Python 3.12.15，faster-whisper 使用 CPU/int8。原始音乐库只读；所有歌词提取、音频裁切和输出保存在被 Git 忽略的 `py-roller-artifacts/validation-20261008/` 中。

- 默认回归套件：258 项通过，覆盖率约 73%。新增 3 项重复区域边界回归测试及 3 项缓存前后结果等价性测试。

完整命令、退出状态、中间 JSON、ASS/LRC 和日志位于上述本地结果目录；`benchmark.py`、`variant.py`、`alignment_probe.py`、`clip_probe.py`、`language_probe.py`、`scaling_probe.py` 保存复现实验的代码。它们引用本机音乐库，不作为公共测试数据分发。

## 时间指标的含义

先从已有 LRC 提取歌词，去除时间戳，再交给流水线。参照时间不传给识别或对齐器。多时间戳行按时间展开，空时间行不计入比较。

表中“中位差/P90 差”是生成行起始时间与已有 LRC 的绝对差，不是经过人工声学标注的准确率。《杀死那个石家庄人》的参考 LRC 带有 py-roller 生成标记，不能充当独立真值。其他 LRC 也未逐行人工复核。现有 LRC 只能验证行级一致性，不能证明逐字/逐音素时间准确。

耗时为本机观察值，包含进程启动、模型加载及输出；期间有其他验证和下载任务，不是受控性能排行榜，不应据此推算其他硬件速度。

## 分离与过滤的对照

同一中文 48 秒片段（原曲 43–91 秒），参照时间统一减去 43 秒：

| 输入与设置 | 行时间中位差（秒） | 歌词覆盖率 | 说明 |
|---|---:|---:|---|
| mix | 0.90 | 82.2% | small；VAD 关 |
| vocals | 1.34 | 44.3% | small；VAD 关 |
| vocals_vad | 0.40 | 81.5% | small；VAD 开 |
| 分离 + noise_gate + dereverb | 1.34 | 48.2% | small；VAD 关；完整六阶段通过 |
| 原始混音，large-v2 | 0.87 | 79.8% | VAD 关；62.34 秒；峰值 RSS 1.56 GiB |

分离、过滤和关闭 VAD 都不能一概视为精度提升。分离后的这个片段反而在开启 VAD 时更好，因此本次不改变默认 VAD。建议先检查识别文本、保留音频长度和质量报告，再进行同片段对照。

本机 Demucs 4.1 首次加载模型停留在 Hugging Face XET 下载路径；确认其进程在等待 XET 后终止该次试验，保留失败日志，再用 `HF_HUB_DISABLE_XET=1` 和 `HTTP_PROXY`/`HTTPS_PROXY` 指向 `http://127.0.0.1:9910` 重试成功。9909 SOCKS 备用未使用。转录器的 HF 选项不控制独立 Demucs 进程的下载，需要为该进程设置环境变量。`--transcriber-local-files-only` 也只约束转录器，不保证首次 Demucs 加载离线。

## 重复歌词回归与修复

真实中文样本在 `few` 模式曾触发 `Matched line anchors must be chronological`。原因是候选路径本身有序，但只替换其中一部分时，新的位置可能越过保留的原匹配。修复为：接受局部替换前检查最终保留的左右邻居，拒绝跨越它们的候选；保留原来的有效匹配。同时修复束搜索跳过一行后遗失上一次时间边界的问题。

这是一项保守的局部修复：互相依赖的多行移动可能因邻居约束而被拒绝；需要全局重复路径搜索时仍使用 `full`。没有通过移动声学锚点掩盖倒序。

另外，为音素对相似度增加最多 4096 项的有界缓存。三种模式的缓存/未缓存测试输出等价（忽略随机单元 ID）。真实英文完整 `full` 单次缓存测试为 66.54 秒，1326 个不同音素对产生约 1.735 亿次缓存命中。原未缓存对照没有留下完整终态结果，因此不报告精确加速倍数。下表使用最终缓存实现重新运行。12 份实际对齐文件另经逐单元校验，匹配单元起止时间与识别产物完全一致。

## 长序列的性能边界

上述真实英文样本的 `full` 完整歌词中位差达 141.50 秒，省略版本为 49.20 秒，说明候选搜索可能选错重复位置；`none/few` 约为 0.46–0.50 秒。此次修复保证时间顺序和避免崩溃，并不证明 `full` 的识别位置正确。该模式在这首歌曲上不适用，仍需与参考及质量报告核对；不能将它作为默认精度升级。

合成等长歌词/音频单元序列，20 单元一行，每单元 0.3 秒；时间轴精确匹配，只测 CPU 对齐而不测识别。分钟数由这个合成单元密度推算，不能直接代表实际歌曲。

| 每侧单元数 | 合成时长 | DP 矩阵格数 | 对齐耗时（秒） | 进程峰值 RSS（MiB） |
|---:|---:|---:|---:|---:|
| 200 | 1 分钟 | 40,401 | 0.11 | 29.2 |
| 1000 | 5 分钟 | 1,002,001 | 2.83 | 64.0 |
| 3000 | 15 分钟 | 9,006,001 | 25.26 | 435.4 |

当前标准 DP 的矩阵空间和主要计算量随两侧单元数乘积增长。音素密集的语言、长音频及 `full` 候选搜索会进一步放大成本。此机器仅 8 GB 内存，建议先串行运行一个模型；并行进程不会共享同一份模型内存。本次没有宣称支持任意长音频，也未执行内存耗尽压力试验。上述 DP 基线测于音素相似度缓存优化之前。

## 语言能力实测

| 路径 | 本机结果 | 边界 |
|---|---|---|
| 中文 zh | 简繁体样本可解析；完整歌曲可运行 | 原文保留；多音字、混合文本和估算时间仍需质量复核 |
| 英文 en | ARPABET 解析与完整歌曲可运行 | 音素时间由词区间分配，不是原生逐音素声学定位 |
| 中文 mul | 中文 IPA 样本可解析 | 字符跨度保留 |
| 英文 mul | gruut 可解析 | 不指定拉丁语言时明确报告默认英语假设 |
| 俄文 mul | gruut 可解析；歌声片段可识别 | 完整歌曲前奏可能误导 ASR 语言检测 |
| 阿拉伯文 mul | gruut 文本解析成功 | 未测试阿拉伯语真实音频，不宣称端到端准确性 |
| 法/德/西/意/葡 mul | 接受语言选择，但本机样本无可用发音单元并报告 unsupported_text | 缺少可用的对应发音数据/引擎；参数存在不等于运行环境支持 |
| 日/韩 mul | 样本无单元并明确报告 unsupported_text | 本次环境没有可用路线；界面翻译与歌词支持是两回事 |

## 发布与后续使用

- 已同步 README 的完成记录、独占临时目录、VAD、硬件限制；新增 CLI 参数帮助进入翻译目录。
- CI 增加严格翻译覆盖检查。本次本机验证不替代 GitHub 的 Linux/Python 版本矩阵，也未执行 Windows/CUDA 实机测试。
- 默认 report 模式允许带诊断输出草稿；程序成功不能视为质量合格。逐单元 strict 会拒绝当前文本派生插值时间。行级 strict 仍检查覆盖率、插值比例和语言警告。
- 用音乐库的 LRC 评估逐字时间是不充分的。若要给出逐字精度结论，需要独立人工标注片段或可靠的字级参考。
- 已保留用户原有未提交改动，没有自动提交、打标签或上传 PyPI。新报告和修复仍属于 Unreleased。
